## 测量方法

Godot 4.6.3 mono / Windows / Compatibility（Intel Arc）。10 Hz 权威逻辑不变，每方五军团、上限 300 人。自然对局不赠送资源、不改敌方 AI、不读取敌方隐藏信息；压力夹具专门补足 600 人并提高生命来持续交火，不能当作自然经济或普通对局帧率。

每个真实 tick 采集命令执行、战略任务、战术提议、补给、移动指挥、编队导航、战斗、视野、快照与报告。帧独立采集实际墙钟间隔、HUD 阶段、表现同步和绘制；截图另存，不进入压力采样。每项采样最多保留前30000个值，超过该上限时不宣称全局分布。耗时原始 JSON 单位 usec，本文表格换算 ms。百分位按排序后 floor((n−1)×p) 取样，帧脚本历史使用 floor(n×0.95)，小样本比较必须保留样本数。

计时区间有包含关系：命令应用包含路线求解，路线求解包含AStar和简化，GameRoot包含HUD刷新，不能把这些P95相加当作一帧总时间。RuntimeMeasurement默认关闭，当前启用测量时世界只由一个线程推进；其静态字典不支持多个世界并发写入，未来worker迁移需改为每世界独立收集器。

CPU 工程测量不等于 GPU query；没有获得可靠 GPU 时间则不填估计值。Godot 帧 delta 可能钳制，host 累积器不等于真实墙钟欠账，不能凭 backlog 很小证明实时运行。固定密集压力基准时不并发其他本任务重负载验证；最终自然局在约tick11000后与功能验证并行，其整局耗时分布不用于性能比较（记录perf23-concurrency-boundary.txt）；用户原有编辑器和旧游戏保留，因此结果是本机条件下的比较，不是跨机器性能保证。

## 查明的问题与实现

- 决策候选在弹药耗尽时反复“敌目标 × 我方成员 × 全单位线性查找”，同快照内预索引成员并计算可开火最低距离，结果逐字段差分验证。
- 表现侧按快照对象身份维护当前/上一帧单位与建筑索引，处理同 tick 换世界、空快照和上一帧改变；不向可变测试快照加入全局 getter 缓存。
- 自主攻击只对合法可见敌人建 tick 内空间桶，查询射程包围盒后仍执行原精准验证、距离排序和平局规则；将领选目标增加覆盖所有成员实际位置/射程的包围盒早退。没有减少攻击频率或视野。
- 战略任务每次推进只筛选/排序一次可能被补入任务的单位，并在每个任务内重新检查归属。包含已分配单位以保留同 pass 释放后重新分配的语义。
- 弹道保留全数量、插值、两层长度/粗细/颜色，外层与内层各批量提交；交叉重叠处合成顺序改变，需实渲检查。
- 终点在计算实际槽位前切换 WIDE，不能用旧纵队槽位宣告展开完成。侦察目标校验使用实际侦察展开宽度。
- 短距追击结束后逐段重连原路线，不可达时不拼接未校验线段；保留归队重试状态，障碍解除可自行继续，新玩家命令仍可取消。
- 大地图加入两秒净位移窗口，识别“每 tick 微动但长时间原地来回”的情况；超过原来三次失败限制后仍按窗口重试，不通过隐藏受阻事件伪造改善。

拒绝主要为无攻击成员 INVALID_DEFINITION 123、目标死亡 ENTITY_DISABLED 107、失去视野 HIDDEN_TARGET 82、组织不足 40；其余是接管/冷却/资源/任务边界。目标在提交与执行之间死亡或离开视野时，执行期拒绝是必要复验，不能为了减少报错取消。无有效攻击成员时仍重复提议值得后续减少，但当前拒绝本身保护了命令契约。

主动联合策略补充发现：economy-final01（并行功能验证，不能作为隔离性能基准）3次参谋批准应用各约9.1秒，首次方案生成约9秒；普通批准提交校验仅约15ms。代码追踪显示`CommanderTaskGraphBuilder.build`每次联合行动重新创建整张大地图导航器，而方案生成另有独立导航缓存。本轮已让任务图复用该合法快照导航缓存，保留原始构造作差分参考；48节点逐字段一致，建筑足迹变化切换缓存。它不接触权威世界导航器，也拒绝真值快照。首次合法快照冷启动仍需构造，不能宣称所有方案生成都已毫秒级；最终隔离结果另列。

自定义0人兵种另发现实际拒绝缺陷：空卡没有编队却仍被军团目标校验要求存在编队，导致整团INVALID_TARGET。本轮已跳过明确0容量的空卡；非零卡缺失编队仍拒绝，policy-diagnostic02覆盖两者。

## 拥堵解释

基线 5700 次 UNIT_STUCK 不是 5700 个不同单位。10秒位移抽样发现63个单位共456个慢移动样本。仅修终点展开后的中间版本有47个持续至少10秒的净无进展片段，最长486秒，说明微动误判和停止尝试确实构成实际问题，不能声称已解决。

新审计按单位、编队、命令签名划分片段，区分恢复推进、改变命令、死亡、进入战斗/抵达/停止和对局结束。判定条件是有编队移动命令、没有攻击目标、距期望槽位大于64且净位移小于32；战斗停车和正常驻守不会算作堵塞。此为工程检测阈值，不等于所有玩家感知停滞。

补员验证使用固定模拟秒桶；每阵营每个固定秒最多5人。tick9与tick10跨越两个秒桶时可连续观察到10人，这是固定秒配额的边界行为，不是滑动一秒限额；报告不会把两者混淆。

最终默认无干预局：30分钟超时平局，31785次发射、1841次命令拒绝、22066次UNIT_STUCK。持续审计记录136片段/40单位/累计7643单位秒，蓝79片段、红57片段，最长577秒（红方突击unit5548）。17片段因恢复推进结束，62因新命令结束，51进入战斗/到达/停止，2死亡，4延续到结算；后两种非恢复状态不能计作“疏通成功”。同单位换命令会分段，因此不能把182秒的新片段与旧486秒直接比较为改善。持续拥堵仍存在，特别是道路边缘、落队成员和编队展开的恢复，需要后续按记录坐标复现。此次修复只证明三项具体缺陷消除，没有证明所有挂机消除。

## 多线程判断

加载仍使用独立线程构造未发布世界，本轮加入资源等待、世界阶段与场景切换计时。正式战斗没有贸然将同一个 world 并发推进：当前 UI/host/存档仍有直接读 world 的路径，直接启动 worker 会引入竞态、丢事件或越权状态写入。独占模拟线程需要命令邮箱、分配 ID/回执、完整事件批次与合法不可变快照的边界迁移，属于独立工作包。CPU 主模拟超过100ms时，单纯挪线程也不会使战局恢复10 Hz实时速度。本轮先落实已测得的重复计算优化，后续依据最终测量决定迁移优先级。

长局进一步指向快照与历史成本：final01（后段有并行负载）快照阶段P50/P95=36.14/147.35ms，战后知识26.18/68.61ms，战术Agent阶段0/120.80ms（每10tick执行，内部含两阵营快照）。这些不是隔离收益数字，但结合代码可确认每次快照仍会遍历并复制本阵营全部任务历史，任务数随对局增长。下一项宜分别测量任务历史、事件窗口和当前态构造，再设计值拷贝的历史分段发布；不能删除复盘事件、共享可变快照或减少AI评估频率来省时。

## 最终测量、策略和流程

待最终版本验证完成后填写，尚不作 PASS 或蓝方胜率结论。原始记录 artifacts/perf23-*；第一次失败日志保留，不计通过。

策略定义均为脚本化玩家指令，不改变游戏规则：

| 策略 | 战前侦察/突击/装甲/火炮 | 战略操作 |
|---|---|---|
| 无干预对照 | 各团12/20/16/12 | 自动将领，无蓝方区域支援 |
| 保守支援 | 同默认 | 储备40、五团各1；受伤集群医院、无友军附近才导弹 |
| 低成本联合推进 | 各团5/45/0/10 | 中路+机动梯队联合推进中路补给链，其余自主 |
| 野区经济转增援 | 中/机5/25/20/10，其余5/45/0/10 | 野区团上野区三点；补员先偏野区，后偏机动；中路联合推进 |
| 集中中路 | 各团10/40/0/10 | 上/中/野/机沿中路补给链逐点推进，下路自主 |
| 炮兵编成 | 各团6/12/12/30 | 将领自主推进，医院和安全导弹支援 |
| 火力支援 | 默认 | 允许少量友伤但敌军至少3倍附近友军，避开己方建筑；净目标至少6人 |

后三种属于针对失败的补充尝试，不能仅凭一种编成的一局结果断言整个蓝方无法获胜。每种方案使用相同公开默认红方模板；不是多随机种子、真人对抗或镜像平衡试验。联合推进需要各非零兵种都可分配，不能把生成失败等同于命令丢失。

复现入口：`tests/tools/perf23_natural.gd -- --strategy=<策略英文ID> --report=res://artifacts/<独立名称>.json --playtest-session=<独立名称>`；策略ID依次为passive/support/economy/jungle/concentration/artillery/fire_support。以Godot4.6.3 mono的`--headless --path . --script res://...`运行。`perf23_render.gd`需真实图形窗口，独立运行；`perf23_flow.gd -- --inspect-debrief`在结算等待实际点击“再战”，不可将等待本身判为卡死。全部日志另存并扫描`SCRIPT ERROR:`和`ERROR:`，不能只看进程退出码。
